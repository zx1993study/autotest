# PunkRecord 功能场景覆盖与执行报告

日期：2026-10-21。测试平台项目：17796。业务环境：用户确认的现有测试环境。

## 结论

原有 70 个场景没有覆盖完整的异常状态与文稿上传链路。本轮保留原场景，累计补充 17 个场景，目前共 9 个功能流程、87 个场景。

按每个场景的最新有效执行统计：**86 个通过，1 个失败**。失败为真实服务行为与预设同名人员处理规则不一致，未放宽断言。未执行的专项不计为通过，也不宣称穷尽所有业务组合。

本轮没有修改 PunkRecord 业务源码、业务数据库结构或直接执行业务 SQL。测试配置通过平台服务保存，业务操作通过 API 完成；本地文件是场景配置、测试样例、辅助导入与执行脚本、结果证据，不是业务功能改造。

### 非早会创建不扣款补充验证

原“周会上传不扣款”仅核对上传后的状态，无法证明会议刚创建时没有临时扣款。新增五类场景将校验分成两个阶段：

1. 有效工作日、考勤政策生效、当天没有早会作为前置；记录全员余额与测试员工流水。
2. 创建非早会，尚未上传文稿，核对会议类型、全员考勤不缺席/不扣款、全员余额完全不变、测试员工流水完全不变。
3. 上传缺席文稿后，再次核对上述状态不变；不会因缺少某位发言人而触发早会扣款。
4. 删除本次新建会议，核对全员余额恢复且没有误创建早会。

| 场景 | 类型 | 最新批次 | 结果 |
|---|---|---|---|
| 21310 | weekly / 周会 | 21325 | 通过 |
| 21311 | project / 项目会议 | 21326 | 通过 |
| 21312 | review / 复盘会议 | 21327 | 通过 |
| 21313 | brainstorm / 头脑风暴 | 21328 | 通过 |
| 21314 | other / 其他 | 21329 | 通过 |

全员查询使用绑定管理员认证的共享用例。流水接口要求必填 `user_id`，因此流水比较限定为专用测试员工，不宣称已经逐个核查全员流水。早期管理员绑定和流水参数配置失败的批次保留，均在创建会议前被拦截；修正后五个场景全部通过。

## 唯一未通过项

**场景 21145，最新批次 21279：文稿同名人员未映射不自动认定出席。**

复现链路：创建当日早会→上传用户提供的 Word 文稿→查询会议详情、员工考勤、管理员考勤、余额与流水→删除本次会议。

证据：

- 环境中有两个有效员工显示名均为 `test_user3`。
- 文稿解析出了 `test_user3`，但会议详情的 `speaker_user_mapping` 为 `{}`，确认没有人为建立映射。
- 服务将账号 `640d1a5c…` 标为 `absent=false, charged=false`，另一个同名员工仍为缺席。
- 管理员查询的 `unmatched_names=[]`，没有提示该同名姓名需处理。
- 被自动选中账号的余额净变化为 0，而当前异常场景预期未确认出席、仍扣 500。

因此不是 HTTP 200 就应通过的问题，而是“同名时未经映射选择了一个员工”的业务识别行为与预设不一致。保留失败结果，未改名、停用员工或补映射来制造通过。需服务端确认同名消歧规则及部署版本后再处理。清理后全员余额恢复。

入口：[早会考勤功能流程](http://127.0.0.1:5173/api/flows/21138)，在运行记录中查看批次 21279。

## 配置修正与断言加强

- 修正 UUID 动态参数：平台不支持直接使用 `{{uuid}}`；改用受支持的随机数字生成器组合合法 UUID 格式，并在执行前验证输入。
- 修正路径参数绑定：新建 API 配置缺少路径字段元数据时，参数未进入实际 URL；改为提取 ID 后绑定变量并明确替换路径，未修改执行器。
- 修正固定余额、固定假期数的旧快照断言：以每次执行前基线核对增减量。
- 按链路核实奖励防重场景的 +30/冲销/再结算断言；拒绝奖励阶段的余额增量应为 0。
- 假期商品价格为 100，批准后余额应减少 100，而非旧快照换算出的 200；余额不足拒绝兑换不应减少年假。
- 空功能清单场景应断言不新增任务，而不是沿用非空清单的“新增 1 个”。该场景没有冒充“删除旧功能任务”规则测试。
- 给 28 个场景中的 49 个异常节点补充业务错误码、错误消息，或字段校验类型与位置断言，强化后全部复跑通过。

符合预期的 400/403/404/422 是异常场景测试通过，不是业务失败。历史配置失败批次仍保留；不能把全部尝试的失败次数当作当前失败场景数。

## 隔离与清理

- 串行执行，避免不同余额、库存、考勤场景相互污染。
- 项目、商品、订单、会议使用本轮新建 ID；不复用旧项目、历史会议或他人订单执行修改。
- 依赖隔离前置的共享 API 用例设置 `requires_flow`，从功能场景中执行，避免误做独立测试。
- 对新建项目、未结束订单、未审批请假和上架商品按 API 能力清理；每个场景核对专用账号的余额、冻结金额与假期恢复。
- 考勤场景删除本次新建会议后核对全员余额与冻结金额恢复，测试日期没有遗留早会。
- 清理和补偿动作单独留证，不会将失败结果改成通过。
- 下架商品、已审批请假、独立待办及业务审计/资金流水等没有删除入口的测试记录会保留。账户恢复不等于抹除测试审计记录，也没有直接删除业务数据库记录。

## 仍待覆盖

以下没有冒充已执行的场景，也未未经确认编造业务规则：

| 待覆盖项 | 本轮限制或下一步 |
|---|---|
| 音频识别的成功、失败、取消与超时 | 当前提供的是 Word 文稿；需音频样例及识别服务测试条件，不能把文稿导入当作音频识别通过 |
| PDF 文稿导入 | 尚无实际 PDF 回归样例，本轮只验证 Word 和无效文稿 |
| 多人并发抢最后一件库存、并发幂等重放 | 本轮为隔离的串行功能回归，尚未进行并发专项 |
| 请假审批与当日考勤联动 | 应使用可撤销的测试日期与数据方案；审批后请假无删除入口，不能修改历史请假或直接改库来恢复 |
| 已归档会议重新上传、归档失败后的补偿 | 还涉及知识库与异步处理，不以普通上传场景替代验证 |
| 不同员工切换、商品改价快照等组合 | 已覆盖核心角色链路，但没有穷尽所有状态交叉组合 |

因此，本轮结论是“主要链路及已确认的异常分支已补充并执行”，不是“全部业务组合 100% 覆盖”。

## 结果证据与验证

- `review-summary.json`：按当前平台配置逐场景核对的最新状态、场景名称、批次 ID、失败节点及来源文件。
- `review-execution.json`：非考勤场景全部执行和复跑证据，包含请求、响应、断言与清理。
- `execution.json`：7 个文稿上传场景首次执行证据。
- `edges-execution.json`：未来日期、非工作日、同名人员继续执行到清理的完整证据。
- `multi-execution.json`：同日多会议链路与双会议清理证据，场景 21308，批次 21309，通过。
- `non-morning-execution.json`：五类非早会的创建阶段、上传阶段、余额/流水断言与清理证据，最新批次 21325—21329 全部通过。
- 本地回归：文件上传、流程执行、参数、准备、持久化，以及本轮配置、非早会分支与清理保护测试，共 **56 项通过**。

结果均来自测试平台真实批次执行，不是仅运行本地模拟断言。
