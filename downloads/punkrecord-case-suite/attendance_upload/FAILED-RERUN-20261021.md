## API 仍失败的业务请求

两个用例属于同一个接口：

`PATCH /api/v1/project/projects/{project_id}/stages/{stage_id}`

| 用例 ID | 测试点 | 新记录 ID | 实际响应 | 未满足的断言 |
|---|---|---|---|---|
| 4325 | 项目阶段交付物纯空格 | 21565 | HTTP 200、code=0，deliverables 仍是三个空格 | 原断言要求 HTTP 400 或 422 |
| 4326 | 项目阶段交付物首尾空格 | 21566 | HTTP 200、code=0，deliverables 两侧空格仍保留 | 原断言要求等于去掉首尾空格后的文本 |

这两条不是请求超时或认证失败。服务确实接受并原样返回了输入。
`deliverables` 是可选交付物文本；“纯空格必须拒绝”是否属于产品规则，仍应与“允许清空可选字段”区分。
本轮按已有断言报告不通过，没有自行放宽断言，也不将可选字段规则争议直接等同于已确认缺陷。

职位、部门、交易方、任务、项目、商品、更新日志、会议、财务账户、交易、合同、请假、任务计划和员工姓名等本轮其余 84 条文本测试通过。
预期拒绝输入得到 HTTP 400/422 时，用例记为通过，不将业务拒绝误计为失败。

场景 21145 的主要差异：

- 文稿出现 `test_user3`，但存在同名员工，且未配置人员映射。
- 服务仍自动将测试账号认定为出席，而不是保留为待确认的同名人员。
- `unmatched_names` 没有按原断言包含 `test_user3`。
- 因此没有产生预期的缺席扣款，余额变化是 0，而非原断言的 -500。
- 流水核对同样失败；这与前面的出席判定差异有关，不能算作另一个已确认独立缺陷。
