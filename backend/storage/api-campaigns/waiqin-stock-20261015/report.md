## 配置结果

## 业务规则与边界

- 每个场景先创建带时间戳和随机后缀的新商品，核对归属后通过采购审批入库准备库存；不用修改库存接口创建不存在的记录，不改已有SKU库存。
- 实际库存 quantity、锁定库存 lockedQuantity、可用库存 availableQuantity 分别断言，不能把HTTP 200当成库存正确。
- 实测采购新增即自动提审，创建后状态1，不能按草稿0断言或再次提交；审批通过直接入库，采购单终态4。现行通用入库单只定义销售/退货来源。
- 因此采购自动入库场景可配置，采购独立确认场景保留为待支持；不伪造来源类型或拿历史入库单凑链路。
- 销售创建阶段库存不变，审批通过锁库；终端销售确认后实际库存和锁定库存同时减少。
- 场景5先审批第一张恰好覆盖库存的销售单，构造实际10、锁定10、可用0，再验证追加销售不能超卖，最后确认发货库存归0。
- 超库存、无库存的创建拒绝场景是严格缺陷探测；若现有服务只在审批时校验，真实执行应报告失败，不自动放宽断言。
- 退货按直接退货和原订单退货分别覆盖；原订单退货只引用本次新销售单和明细，可退余额不足时拒绝。
- 终端退货待确认单 sourceType=2，来源仓库0、目标为退货仓，待确认状态2；确认后入库状态1、退货单状态5。
- 库存流程不包含权限测试，只核对拆箱、销售、退货等操作前后的数量、锁定和可用库存变化。
- 拆箱补件使用两种独立商品，双向、刚好可用、缺参、非正数量、同商品、源库存缺失、锁定库存均核对两侧变化。
- 异常断言不把未知HTTP/业务500当成功；业务500若为合理拒绝，应先实测并确认精确错误契约再维护白名单。
- 采购创建用角色2认证；审批与仓库确认用实测用户1/仓库管理员认证，不执行其他角色权限反例。
- 所有确认单ID来自本场景来源订单查询，并核对来源类型/ID、商品、数量、仓库和状态，任一不符即停。
- 不支持从正式用例列表单独运行节点；应从API功能管理的功能场景执行。

## 执行注意

离线模拟通过不代表外部业务执行通过。真实执行会新增商品、订单和库存流水，不自动删除或清理；仅限测试环境。
旧审批流程及已有CRUD功能流程保持不变。运行前应确认认证未过期，且仓库管理员、审批节点与接口契约仍匹配。
采购、销售、退货的实测异常按运行记录单独分析；不把未知500或未到达最终库存核对的场景当成通过。
