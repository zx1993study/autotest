## 链路与保护

1. 每个通过/拒绝场景独立创建数据，名称包含自然业务名称、时间戳及随机后缀。
2. 列表按唯一标记定位且必须恰好一条；详情再次核对业务主键、名称及待审批状态。
3. 客户从详情顶层 approvalProcess 读取实例，其余业务从详情 approvalInstanceId 读取。
4. 审批信息必须匹配本次业务ID、实例ID、业务类型和工作流，且恰好一个当前待审批节点、审批用户ID=1。
5. 使用已核对为用户1的 admin-api 认证审批；实例/节点ID由前置响应关联，不能填历史ID。
6. 审批后同时核对流程结果、节点结果、审批用户和业务状态，并再次核对业务关联实例。HTTP 200 不等于审批成功。
7. 活动先创建独立类型/申请模板及其专属工作流、审批节点；不变更已有类型、默认工作流或账号角色。
8. 活动申请先完成新活动的通过审批，再创建独立申请工作流和申请，最后执行申请的通过/拒绝。
9. 节点用例需要场景输入与前置ID；直接从正式用例列表单独执行会在发请求前失败。应从审批流程的功能场景执行。

## 注意事项

- 离线测试覆盖18个模拟通过/拒绝分支及创建人与审批人的独立认证；模拟结果不等于外部服务真实业务执行通过。
- 采购创建者需角色2，直营销售创建者需角色112；仅绑定已通过登录及 /getInfo 实测的专用账号，不修改已有角色权限或默认审批配置。
- 当前启用链路覆盖现有单节点审批；若审批改为多节点或换审批人，用例会停止，需同步真实审批配置及认证。
- 原始旧模板保存在同目录 backup-flow-11775.json；旧接口已失效，新模板中的旧节点未绑定用例，所有新增场景均跳过。
- 库中还有历史 visit_plan 实例，但无现行审批定义，当前审批详情接口返回业务500；没有把历史记录当成可执行审批能力。
- 活动与申请时间在模板输入中维护。超过活动有效期后需更新 activity_start_time/activity_end_time/start_time/end_time，再执行。
- 真实执行会在外部测试环境留下新客户、单据、活动类型和工作流；本次不做自动删除，不触发出入库确认或活动兑付。
